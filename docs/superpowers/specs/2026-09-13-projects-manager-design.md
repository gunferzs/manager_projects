# Менеджер запущенных проектов — дизайн (этап 1)

Дата: 2026-09-13  
Статус: на ревью  
Этап: локальный менеджер на этой машине. Удалённые серверы и деплой — отдельный этап, в этой спецификации не реализуются.

## Цель

Веб-пульт на домашней машине: видеть какие проекты запущены, где они доступны (только машина / локальная сеть), запускать и останавливать их через Docker Compose, открывать порты в фаерволе Windows при запуске в локалку.

Сервис будет доступен из интернета по домену (проброс порта + TLS). VPN и туннели не используем: WireGuard не проходит белые списки сетей, из которых нужен вход. Единственный барьер — авторизация в приложении.

## Решения, которые уже приняты

| Тема | Решение |
|------|---------|
| Граница этапа | Только локальная машина. Таблиц серверов и размещений нет |
| Стек | Один процесс Next.js (App Router) + SQLite + Docker Compose на хосте |
| Периметр | Публичный HTTPS, без VPN |
| Вход | Ключ + TOTP (когда TOTP включён). Два экрана |
| Challenge | Короткоживущий, без сессии, **привязан к IP** |
| Статус | Не хранится. Читается из Docker + каскад проб |
| Доступность | Вычисляется из bind порта и правил фаервола |
| Операции | Очередь задач + лог, не синхронный HTTP на весь `compose up` |
| Контракт проектов | Работаем с существующими compose как есть, чужие репозитории не правим |

## Архитектура

Один процесс Next.js слушает локальный порт (например `127.0.0.1:3100`). Снаружи его закрывает Caddy: 80/443, TLS, прокси на приложение. Приложение само не публикует 443.

Слои внутри процесса:

1. **Доступ** — мастер-установка ключа, логин, TOTP, сессии, guard на все страницы, API и server actions.
2. **Реестр** — SQLite: описание проектов и сервисов. Живое состояние приходит из Docker в момент запроса.
3. **Операции** — задачи `start` / `stop` / `restart` / `scan`, построчный лог.
4. **Фаервол** — отдельный привилегированный помощник с белым списком команд. Веб-процесс от администратора не запускается.

Корневой экран приложения — список проектов. Новые экраны подключаются только из этого флоу: вход → список → деталка / настройки / диалог запуска.

## Авторизация

### Роли cookie

| Cookie | Что даёт | Срок |
|--------|----------|------|
| нет | только `/login`, `/setup` (если ключа ещё нет), статика логина | — |
| `challenge` | только `GET /login/totp` и `POST` проверки TOTP | 2–5 минут, одноразовый успех |
| `session` | весь остальной UI и API | короткая сессия (часы, не недели), продлевается при активности |

`challenge` не является сессией: любой запрос к списку, деталке, настройкам, задачам и Docker с этой cookie получает 401 и редирект на `/login`.

### Мастер-установка (ключа ещё нет)

Если в `auth_settings` нет хеша ключа — это не логин, а `/setup`: два поля нового ключа (должны совпасть), минимальная длина 16 символов. После сохранения — сразу `session` и редирект на список. TOTP на этом шаге не спрашиваем и не включаем.

Повторный заход на `/setup` при уже существующем хеше — редирект на `/login`.

### Экран 1: ключ (`/login`)

Поля: ключ, кнопка «Войти». TOTP на этом экране нет.

- Ключ неверный → одна и та же фраза «Неверные данные». Не различаем «нет такого ключа» и «нужен TOTP».
- Ключ верный, TOTP **выключен** → создаём `session`, редирект на исходный URL или `/`.
- Ключ верный, TOTP **включён** → `session` не создаём, данные проектов не отдаём. Ставим `challenge` (случайный токен, в БД — хеш, IP клиента, срок, счётчик попыток). Редирект на `/login/totp`.

### Экран 2: TOTP (`/login/totp`)

Только поле из 6 цифр. Без валидного незаexpired `challenge` — редирект на `/login`.

- Код неверный → «Неверные данные», счётчик на этом challenge. После лимита (5 попыток) challenge сжигается, пользователь на `/login`.
- Код верный → challenge сжигается, создаётся `session`.

### Привязка challenge к IP

IP клиента фиксируется в момент успешного ввода ключа. Проверка TOTP принимается только с того же IP.

Как берём IP: запрос приходит от Caddy на localhost, поэтому смотрим первый адрес из `X-Forwarded-For`, которому доверяем только от loopback. Прямой `req.socket.remoteAddress` без прокси — если Caddy ещё не стоит (локальная разработка).

Известный компромисс (принят): между двумя экранами смена сети (Wi‑Fi → LTE, CGNAT) оборвёт вход. Пользователь вводит ключ заново. Сессию после успеха к IP **не** привязываем: с телефона в другой сети уже открытый менеджер продолжает работать.

### Блокировка

Счётчик неудачных попыток ключа живёт в `auth_settings`. После 8 неудач подряд — `locked_until` на 15 минут. В ответе не говорим, ключ это или TOTP: «Попробуйте через N минут». Успешный вход сбрасывает счётчик.

### Смена секретов

- Сменить ключ: старый ключ + новый (дважды) + текущий TOTP, если TOTP включён. После смены все сессии кроме текущей сбрасываются.
- Включить TOTP: в настройках показываем QR и секрет **один раз**, подтверждаем кодом. После подтверждения секрет больше не отдаём.
- Перевыпустить TOTP: текущий код старого TOTP (или ключ, если TOTP ещё не было — этот путь только для включения), затем новый QR. Старые challenge сжигаются.

### Guard

Один серверный модуль проверяет cookie до рендера страницы, до API route и до server action. Обхода через «забытый» route быть не должно: тесты перечисляют открытые пути (whitelist: `/login`, `/login/totp`, `/setup` при пустой базе, `_next` статика). Всё остальное закрыто.

## Модель данных

SQLite-файл на диске машины (путь из env, по умолчанию рядом с приложением, не в git). Секреты в полях шифруются мастер-ключом из env (`MANAGER_MASTER_KEY`). Хеши — argon2id. В API секреты не возвращаются.

### `auth_settings` (одна строка)

- `key_hash`
- `totp_secret_encrypted` (null, пока TOTP не включён)
- `totp_enabled` (boolean)
- `failed_attempts`
- `locked_until`
- `updated_at`

### `auth_challenges`

- `token_hash`
- `client_ip`
- `expires_at`
- `attempts`
- `created_at`

### `sessions`

- `token_hash`
- `created_at`, `expires_at`, `last_seen_at`
- `ip`, `user_agent` (для аудита, не для отказа в доступе)

### `projects`

- `id`, `slug`, `name`, `description`, `image_path`
- `root_path`, `compose_file`, `compose_project`
- `source`: `discovered` | `manual`
- `enabled`
- `created_at`, `updated_at`

### `project_services`

- `project_id`
- `name`
- `container_name` (nullable)
- `host_port` (nullable)
- `health_kind`: `http` | `tcp` | `docker` | `none`
- `health_path` (например `/health`)
- `is_primary` — участвует в сводном чипе проекта
- `is_ui` — есть кнопка «Открыть»

### `jobs`

- `project_id`
- `type`: `start` | `stop` | `restart` | `scan`
- `target_access`: `machine` | `lan` (для start/restart)
- `status`: `queued` | `running` | `succeeded` | `failed` | `cancelled`
- `error_summary`
- `started_at`, `finished_at`

### `job_logs`

- `job_id`, `seq`, `at`, `stream` (`stdout` | `stderr` | `system`), `line`

### `audit_events`

- `at`, `action`, `project_id`, `job_id`, `session_id`, `ip`, `outcome`, `detail` (JSON без секретов)

Таблиц `servers` и `deployments` нет. Когда появится этап 2, у `jobs` добавится nullable `server_id`.

## Живой статус и доступность

При открытии списка и деталки:

1. Ищем compose-проект по `compose_project` (и по пути конфига, если имя пустое).
2. Нет контейнеров → статус `stopped`, чип «не запущен».
3. Есть контейнеры, ни один не `running` → `stopped` / `exited`.
4. Есть `running` → docker healthcheck, если Docker его знает.
5. Для каждого `project_services` с `http`/`tcp` — проба с хоста (localhost + порт).
6. Сводный чип:
   - зелёный `running`, если все `is_primary` живы;
   - жёлтый `degraded`, если контейнеры up, а HTTP/health не отвечает;
   - красный `unhealthy`, если основные пробы явно упали;
   - серый `stopped`.

Доступность (второй чип), только для запущенного проекта:

- все публикуемые порты на `127.0.0.1` → «только машина»;
- есть bind `0.0.0.0` (или `::`) и на эти порты есть **наши** правила фаервола → «локалка»;
- bind `0.0.0.0`, правил нет → жёлтый «локалка без фаервола» (порт может быть уже виден в LAN из‑за Docker Desktop, но мы это не подтверждаем);
- чипа «интернет» на этапе 1 нет.

Каскад проб не требует health-ручки у каждого проекта: нет пути — остаёмся на docker/TCP.

## Операции запуска

Диалог: «Только эта машина» или «Локальная сеть».

- `machine`: `compose up` с публикацией портов на `127.0.0.1`. Фаервол не трогаем. Если compose-файл жёстко прописывает `0.0.0.0` и не принимает overlay — в логе пишем предупреждение и всё равно стартуем как есть; чип доступности покажет факт, не намерение.
- `lan`: проверяем, что помощник фаервола доступен (elevation). Если нет — **останавливаемся до** `compose up` и показываем, что нужно подтвердить UAC / запустить помощник. Если да — открываем правила на порты `is_primary`/`is_ui` и внутренних API проекта, затем `compose up`. Где возможно, публикуем на `0.0.0.0`.

Перед стартом: занятость портов. Конфликт → задача `failed`, в логе кто слушает (процесс или контейнер).

Пока по проекту есть `running` job типов start/stop/restart — повторные кнопки неактивны, виден лог текущей задачи.

Стоп: подтверждение в UI, затем `compose stop` (или `down` без `-v`, тома не удаляем). Для `lan` после стопа снимаем **только** правила с нашим префиксом имени, которые открывали для этого проекта.

Перезапуск = стоп + старт с тем же `target_access`, что был у последнего успешного start, либо выбор в диалоге, если запускаем из остановленного.

Скан (`scan`): `docker compose ls --all` + обход путей из настроек. Новые compose-проекты создают `projects` + черновые `project_services` (порты из YAML). Уже известные не затирают имя, описание и картинку.

## Фаервол (Windows)

Отдельный помощник (маленький бинарник или подписанный скрипт), который веб-процесс вызывает локально.

Белый список действий:

- `allow --name <rule> --port <n>`
- `revoke --name <rule>`
- `list --prefix <prefix>`

Имена правил: префикс `mgrproj-` + slug + порт. Другие правила системы не трогаем. Помощник не принимает произвольный `netsh`.

Без elevation помощник завершается понятным кодом, UI не делает вид, что локалка открыта.

## Экраны

### `/setup`

Только если ключа нет. Два поля ключа. После успеха — список.

### `/login`

Ключ. Ошибки общие. Если залочено — «Попробуйте через N минут».

### `/login/totp`

Код. Назад на `/login` сбрасывает challenge.

### `/` — список (корень)

Шапка: название, текущий LAN-IP (диагностика), ссылка в настройки. Карточки: имя, превью, чип статуса, чип доступности, порты. Не запущен — «Запустить». Запущен и есть `is_ui` — «Открыть» (URL `http://<lan-ip>:<port>` для lan-статуса, иначе `http://127.0.0.1:<port>`). Клик по карточке — деталка.

Пустой реестр: «Найти проекты на машине».

Состояния: скелетон при загрузке; баннер «Docker недоступен» и мёртвые кнопки старта; на карточке без compose — чип «нет Docker», старта нет.

### `/projects/:slug` — деталка

Фото, имя, описание. Контролы: запустить / остановить / перезапустить (стоп с confirm). Тот же диалог среды. Таблица сервисов: имя, порт, результат последней пробы. Лог текущей или последней задачи, опционально история jobs этого проекта. Ссылка назад на список.

Проект без compose: текст почему нельзя запустить, без кнопок up.

### `/settings`

Три блока, без вкладки серверов:

1. Безопасность — сменить ключ, включить/перевыпустить TOTP.
2. Машина — LAN-IP, профиль сети Windows (`Private` / `Public` / неизвестно), список путей скана (редактируемый), кнопка скана.
3. Аудит — последние события.

После первого входа, пока TOTP выключен — заметный баннер в шапке и в настройках: «Включите TOTP до публикации в интернет». Это не блокирует работу локально.

## Настройки машины, нужные для локалки

Чтобы «запустить в локалку» имело смысл, менеджер знает и показывает:

1. LAN-IPv4 этой машины (для ссылок «Открыть» и для человека с телефоном).
2. Профиль сети Windows — если `Public`, правила `private` могут не сработать; показываем предупреждение в диалоге `lan`.
3. Список путей, где лежат проекты (по умолчанию `C:\Users\gunfe\projects` и домашняя папка пользователя — оба корня, которые уже есть на машине).

Подставлять LAN-IP в `NEXT_PUBLIC_*` чужих проектов менеджер **не** умеет: чужие репозитории не меняем. Если фронтенд проекта зашит на `localhost`, в деталке это можно описать текстом, но чинить за них не входим в этап 1.

## Безопасность (кроме входа)

- Никаких произвольных команд из UI. Только именованные операции: start, stop, restart, scan, firewall allow/revoke.
- Caddy терминирует TLS. Приложение слушает localhost.
- Cookie: `HttpOnly`, `SameSite=Strict`, `Secure` когда запрос пришёл по HTTPS.
- CSRF: server actions / origin check. Формы логина — POST.
- Аудит каждого start/stop/restart/смены ключа/TOTP.
- Мастер-ключ шифрования и хеш входа — разные сущности. `MANAGER_MASTER_KEY` не является ключом логина.
- Логи задач не содержат ключ входа и TOTP-секрет.

## Тестирование

Стек: Node.js test runner + TypeScript, файлы рядом с кодом (`*.test.ts`). TDD: сначала падающий тест, потом реализация. Перед заявлением «готово» гоняем этот набор.

Обязательные кейсы:

1. Guard: аноним, `challenge`, `session` — кто куда пускается. Whitelist путей.
2. Setup: пустая база пускает `/setup`; после ключа `/setup` закрыт.
3. Логин: неверный ключ; верный без TOTP → сессия; верный с TOTP → только challenge, без доступа к `/`.
4. TOTP: чужой IP с тем же challenge → отказ; верный IP + верный код → сессия; 5 неверных кодов → challenge мёртв.
5. Блокировка после 8 неверных ключей.
6. Статус: фикстуры Docker (нет контейнеров / running / unhealthy / HTTP 200 / TCP closed).
7. Доступность: bind `127.0.0.1`; bind `0.0.0.0` с нашим правилом; без правила.
8. Задачи: конфликт порта; второй start, пока первый `running`.
9. Помощник фаервола: разбор argv, отказ на неизвестную команду, без реального `netsh` в CI.
10. Скан: из фиктивного `compose ls` создаются проекты и не затирают ручное описание.

Интеграция с настоящим Docker — отдельный opt-in, не обязателен в CI.

## Вне скоупа этапа 1

- Серверы, SSH, GitHub deploy key, установка Docker на Ubuntu, подбор портов на VPS, Caddy на чужой машине.
- Правка compose/env в соседних репозиториях.
- Произвольный терминал в UI.
- Мультипользовательность (один ключ на всю установку).
- Мобильное нативное приложение.

## Порядок реализации (ориентир)

1. Каркас Next.js, SQLite, setup + двухшаговый логин + guard + тесты доступа.
2. Модель проектов, скан, список со статусами (мок Docker в тестах).
3. Деталка, задачи start/stop, логи.
4. Диалог среды, фаервол-помощник, чип доступности.
5. Настройки, аудит, Caddyfile, скрипт локального запуска на `0.0.0.0` только если явно понадобится отладка с LAN; по умолчанию приложение слушает localhost за Caddy.
